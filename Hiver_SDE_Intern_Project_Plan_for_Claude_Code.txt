HIVER SDE INTERN TAKE-HOME ASSIGNMENT
IMPLEMENTATION PLAN FOR CLAUDE CODE
====================================

PROJECT GOAL
------------
Build a brand-specific AI customer-support agent using the Customer Support on Twitter
dataset.

For a new customer message, the system must:
1. Identify the customer's intent.
2. Retrieve similar historical support conversations.
3. Draft a reply grounded in those historical cases.
4. Decide AUTO_HANDLE vs ESCALATE.
5. Give a reason for the escalation/handling decision.
6. Prove the system works using a manually labelled golden evaluation set,
   baselines, automated metrics, and an LLM-as-judge validated against humans.

IMPORTANT
---------
- Do NOT train an LLM from scratch.
- The historical Twitter conversations are primarily used as support knowledge/evidence.
- Build the project incrementally. Do not implement everything at once.
- Keep every component understandable because the candidate must explain and modify
  the code live.
- Prefer simple, reproducible solutions over unnecessary complexity.
- Do not use the full ~3M tweet dataset for every experiment. Use a justified subset.
- Keep the golden evaluation set isolated from the data used to build/tune the system.
- Every major decision should be recorded in DECISION_LOG.md.

FINAL HIGH-LEVEL PIPELINE
-------------------------
Customer Message
       |
       v
Preprocessing
       |
       v
Intent Classification
       |
       v
Retrieve Similar Historical Cases
       |
       v
Grounded Reply Generation
       |
       v
Escalation / Auto-Handle Decision
       |
       +------------------+
       |                  |
       v                  v
AUTO_HANDLE           ESCALATE
       |                  |
       v                  v
Draft Reply          Human Agent

OBJECTIVE

SELECTION CRITERIA

1. Sufficient number of conversations.
2. Clear customer-support interactions.
3. Diverse but understandable problems.
4. Consistent historical resolutions.
5. Enough data for train/dev/test or knowledge/evaluation splits.
6. Minimal noise compared with alternatives.

2. Inspect representative conversations.
3. Select one brand.
4. Record the decision and reasoning in DECISION_LOG.md.

SELECTED_BRAND = "BrandName"

PHASE 3 — CLEAN AND RECONSTRUCT CONVERSATIONS
==============================================

OBJECTIVE
---------
Transform messy tweets into usable customer-support cases.

TASKS
-----
Build a preprocessing pipeline that:
1. Removes obvious unusable rows.
2. Handles missing values.
3. Removes duplicates where appropriate.
4. Identifies customer messages.
5. Identifies brand/support replies.
6. Reconstructs conversation context when possible.
7. Groups related messages into conversation/case records.
8. Preserves timestamps and IDs.
9. Keeps original text available for traceability.
10. Creates a deterministic train/knowledge/evaluation split.

Recommended normalized record:

{
  "conversation_id": "...",
  "customer_message": "...",
  "brand_response": "...",
  "context": [...],
  "timestamp": "...",
  "brand": "...",
  "source_ids": [...]
}

If multi-turn context is available, preserve it rather than reducing
everything to a single tweet.

OUTCOME
-------
Generate a clean dataset such as:
- data/processed/support_cases.jsonl
- data/processed/support_cases_sample.jsonl
- preprocessing statistics

Also produce:
- number of usable cases
- number of multi-turn conversations
- percentage removed
- examples before/after preprocessing

SUCCESS CRITERIA
----------------
A human can inspect 20–50 random cases and understand exactly what
customer problem and historical brand response the system is using.


PHASE 4 — DISCOVER AND DEFINE INTENTS
=====================================

OBJECTIVE
---------
Create a small set of customer-support intent categories based on the
selected brand's actual data.

IMPORTANT
---------
Do NOT blindly use Banking77's 77 labels.
Do NOT create dozens of unnecessary intents.

Target approximately 8–15 useful intents, depending on the data.

TASKS
-----
1. Sample a representative set of customer messages.
2. Use clustering/LLM analysis only as assistance for discovering themes.
3. Inspect representative examples for every proposed category.
4. Merge overlapping categories.
5. Remove categories with too little useful data unless they are important.
6. Define each final intent in plain English.
7. Define positive examples and boundary cases.
8. Create a stable label mapping.

Example format:

refund:
    description: Customer is asking about a refund, refund status,
                 or missing refund.
    examples:
        - "Where is my refund?"
        - "I requested a refund but haven't received it."

OUTCOME
-------
Generate:
- src/intents/labels.py or config/intent_labels.json
- docs/intent_definitions.md
- intent distribution report
- representative examples per intent

We should be able to explain every intent in one or two sentences.

SUCCESS CRITERIA
----------------
Two people reading the intent definitions should generally agree on
which label a customer message belongs to.


PHASE 5 — BUILD THE GOLDEN EVALUATION SET
=========================================

OBJECTIVE
---------
Create 150–250 manually labelled examples that serve as the main
ground-truth evaluation set.

THIS IS CRITICAL.

TASKS
-----
1. Sample messages across all final intents.
2. Avoid sampling only the easiest/common examples.
3. Include ambiguous and difficult cases.
4. Include rare but important intents.
5. Manually assign:
   - intent
   - expected action: AUTO_HANDLE or ESCALATE
   - optional notes/reason
6. Keep these examples isolated from the knowledge/index data used for
   final evaluation.
7. Record how sampling and labeling were performed.
8. If possible, have a second human review a subset for label consistency.

Recommended schema:

{
  "id": "...",
  "customer_message": "...",
  "gold_intent": "...",
  "gold_action": "AUTO_HANDLE",
  "gold_notes": "..."
}

OUTCOME
-------
Generate:
- data/golden/golden_set.jsonl
- data/golden/golden_set.csv
- docs/golden_set_methodology.md

The methodology must explain:
- sample size
- sampling strategy
- label definitions
- how difficult cases were included
- how leakage was avoided

SUCCESS CRITERIA
----------------
We have 150–250 trustworthy examples that were not used to directly
teach the final system.

PHASE 9 — BUILD HISTORICAL CASE RETRIEVAL
=========================================

OBJECTIVE
---------
Find historically similar customer-support cases for every new query.

This is the knowledge/retrieval part of the system.

TASKS
-----
1. Take historical support cases NOT belonging to the golden evaluation set.
2. Create embeddings for customer messages/cases.
3. Store vectors in FAISS or another simple vector index.
4. For a new customer message:
   a. create its embedding
   b. search for top-k similar cases
   c. return the historical customer message + brand response
5. Preserve source IDs so evidence can be traced back.
6. Measure retrieval quality separately if possible.

Start with top_k = 3 or 5.

OUTCOME
-------
Generate:
- src/retrieval/embeddings.py
- src/retrieval/retriever.py
- local vector index
- retrieval examples
- retrieval evaluation statistics

Example output:

Query:
"My refund still hasn't arrived."

Retrieved:
1. Customer: "Where is my refund?"
   Brand: "Please DM your transaction ID..."
2. Customer: "Refund is pending..."
   Brand: "We'll check the status..."
3. Customer: "I haven't received my refund..."
   Brand: "Please send your reference number..."

SUCCESS CRITERIA
----------------
Retrieved cases should usually be genuinely relevant, not merely
lexically similar.


PHASE 10 — BUILD GROUNDED REPLY GENERATION
==========================================

OBJECTIVE
---------
Generate a useful reply using the customer's query, intent, and
historical evidence.

INPUT TO LLM
------------
1. Customer message
2. Predicted intent
3. Top historical cases
4. Strict instructions to stay grounded

CORE RULE
---------
The LLM must NOT invent:
- policies
- refund amounts
- deadlines
- guarantees
- account actions
- facts not supported by the evidence

If the evidence is insufficient, it should recommend escalation instead
of hallucinating an answer.

Recommended structured output:

{
  "draft_reply": "...",
  "evidence_ids": ["...", "..."],
  "grounding_note": "..."
}

OUTCOME
-------
Generate:
- src/generation/reply_generator.py
- example generated replies
- stored evidence used for each reply

SUCCESS CRITERIA
----------------
A reviewer can trace important claims in the reply back to historical
support evidence.


PHASE 11 — BUILD ESCALATION DECISION
====================================

OBJECTIVE
---------
Decide whether the AI should handle the case or send it to a human.

IMPORTANT PRINCIPLE
-------------------
Escalation is a feature, not a failure.

The agent should prefer escalation when it lacks sufficient evidence
or when the issue is high-risk.

POSSIBLE ESCALATION SIGNALS
---------------------------
- Potential fraud/payment dispute
- Legal threats or highly sensitive complaints
- Repeated unresolved issues
- Low intent confidence
- Poor retrieval similarity
- No useful historical examples
- Conflicting historical resolutions
- Other high-risk categories identified from the selected brand

AUTO-HANDLE SIGNALS
-------------------
- Common intent
- High confidence
- Strong retrieval evidence
- Consistent historical resolutions
- Low-risk issue

TASKS
-----
Create a decision module that returns:

{
  "decision": "AUTO_HANDLE",
  "reason": "Common issue with strong historical evidence..."
}

or:

{
  "decision": "ESCALATE",
  "reason": "Insufficient historical evidence..."
}

Avoid arbitrary thresholds. Make thresholds configurable and tune them
using validation data, not the golden set.

OUTCOME
-------
Generate:
- src/escalation/decision.py
- escalation rules/config
- examples of auto-handle and escalation decisions

SUCCESS CRITERIA
----------------
The system should be conservative about unsafe automatic responses.

PHASE 16 — "WHAT IS MISLEADING ABOUT MY HEADLINE NUMBER?"
==========================================================

OBJECTIVE
---------
Challenge our strongest result.

Example headline:
"Our intent classifier achieves 91% accuracy."

Then investigate:
- Class imbalance
- Easy vs difficult examples
- Rare intent performance
- Golden-set size
- Data leakage risk
- Human labeling uncertainty
- Reply quality vs intent accuracy
- Escalation mistakes hidden by overall accuracy

Possible conclusion:
"91% overall accuracy is misleading because common intents dominate
the evaluation set and minority-intent macro F1 is substantially lower."

OUTCOME
-------
A mandatory report section that honestly qualifies the headline metric.

IMPORTANT GUIDELINES FOR CLAUDE CODE
====================================

When implementing each phase:

1. Implement ONLY the current phase unless explicitly asked otherwise.
2. Before changing architecture, explain why the change is needed.
3. Keep functions small and testable.
4. Add tests for important logic.
5. Save intermediate outputs to files so results are inspectable.
6. Never silently discard data; report filtering statistics.
7. Never leak golden-set examples into training/index construction.
8. Never hard-code evaluation results.
9. Never claim a metric without saving the underlying predictions.
10. Keep API/model configuration in environment variables or config files.
11. Use deterministic random seeds for sampling where possible.
12. Log important decisions.
13. Prefer simple implementations that can be explained in an interview.
14. Do not over-engineer the frontend.
15. Do not build production Twitter integration; this is an offline AI
    support-agent prototype.
16. Do not train an LLM from scratch.
17. Do not allow the LLM to invent unsupported customer-support policies.
18. Treat escalation as a valid and desirable outcome when evidence is weak.
19. When a result is unexpectedly high, investigate possible leakage before
    celebrating it.
20. Every major result should be reproducible with one command.


THE CORE IDEA TO REMEMBER
=========================

This project is NOT:

"Train an LLM on 3 million tweets."

It IS:

"Use historical customer-support conversations from ONE brand to build
a small AI support agent that understands a new customer message,
finds similar past cases, drafts a grounded response, and knows when
to hand the case to a human — then rigorously prove how well it works."

The most important part of the assignment is not making the AI look
impressive. It is demonstrating:
- what works,
- what does not work,
- why it fails,
- when it should escalate,
- and whether our evaluation itself can be trusted.
